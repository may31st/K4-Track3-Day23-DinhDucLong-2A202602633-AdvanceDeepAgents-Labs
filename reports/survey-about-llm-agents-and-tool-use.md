# LLM agents and tool use: methods, evaluation, coordination, and safety

## TL;DR

- Early work made the agent loop explicit: ReAct alternates reasoning with actions and observations, while Toolformer learns when and how to invoke APIs through self-supervised training. [1][2]
- Recent tool-use work ranges from generated executable functions to supervised tool learning and outcome-reward reinforcement learning, but the reported results use different tasks and cannot be ranked on one scale. [3][4][5]
- Better evaluations measure decisions and tool-call trajectories, not only final answers; the available studies find problems with call/no-call choices, difficult tool retrieval, and longer dependent sequences. [6][7][8]
- Delegation, security, and oversight remain practical constraints: multi-agent results depend on the tested setting, tool-connected agents can still fail under prompt injection, and oversight benchmarks are only beginning to assess consequential decisions. [9][10][11][12]

## Background

I treat an LLM agent as a model that selects and executes actions over multiple steps, often through tools such as search, code execution, APIs, or a computer interface. Tool use adds an action boundary to ordinary text generation: the model has to decide whether an external operation is needed, choose a tool, supply valid arguments, interpret the result, and decide what to do next. The papers below study different parts of this loop, so a reported gain on one task is not evidence of a general-purpose agent improvement.

Two foundational designs clarify the field's starting points. ReAct represents the interaction as an explicit sequence of reasoning traces, actions, and observations, allowing retrieved information or environment feedback to affect later steps. Its authors report results on question answering, fact verification, and interactive tasks; for ALFWorld and WebShop, one- or two-example prompting exceeded the listed imitation or reinforcement-learning baselines by 34 and 10 percentage points in success rate, respectively. Those figures belong to those benchmark setups, not a general agent capability score. [1] Toolformer shifts part of the burden from prompting to model training: it generates candidate API calls, executes them, retains calls that help predict future text, and fine-tunes the model on the resulting examples. The authors report improved zero-shot results on the tested tasks, including with a 6.7-billion-parameter model, but this method focuses on API invocation and response integration rather than all parts of long-horizon control. [2]

Tool-use awareness also became an explicit evaluation target. MetaTool asks whether models should use a tool and which available tool to choose; its HF summary describes substantial room for improvement, although the summary does not provide detailed scores or protocol. [6] For collaborative agents, LLM-Coordination offers a related foundation: its benchmark separates environment comprehension from Theory of Mind and joint planning, and reports stronger performance on some environment tasks than on those social-reasoning components. Its four coordination games give a useful early test, but do not by themselves establish reliable open-ended delegation. [13]

## From fixed tools to learned and composable actions

Recent methods vary in what they let the model change. DynaSaur proposes generating and composing programs written in a general-purpose programming language, then accumulating generated actions for future reuse. This gives an agent a route beyond a fixed action menu when an action is missing or a sequence needs composition. The authors report improved flexibility and performance across several benchmarks, including recovery when predefined actions are absent or fail. The retrieved evidence does not supply benchmark-specific effect sizes, and generated code execution adds safety and runtime concerns. [3]

AutoTools addresses the preparation of callable tools: it proposes extracting tool documentation into functions, checking syntax and runtime behavior, and composing those functions into programs. Its AutoTools-Learning collection contains 34,000 synthetic examples across documentation understanding, tool relevance, and function programming. This gives a concrete training-data approach, though the publisher abstract retrieved for this survey does not provide numerical result details or establish transfer to arbitrary APIs. [4]

Tool-R1 instead uses outcome-based reinforcement learning for multi-step tool use through executable Python, with shared variables across steps and a queue that reuses high-quality trajectories. The authors report that a Qwen2.5-7B model's GAIA answer accuracy rose from 10.30% before training to 19.39% after training, using about 1,300 question-answer pairs. Their ablation reports reduced training time with the dynamic queue. This is evidence for the particular training recipe and GAIA evaluation; answer accuracy alone does not show whether every intermediate call was correct or robust. [5]

These approaches suggest different engineering tradeoffs. A fixed API schema can constrain the actions available to the model, while generated functions can be more flexible but harder to inspect and safely execute. Supervised examples directly teach recognized subtasks; outcome rewards can train multi-step behavior without requiring a label for every call, but depend on a reliable reward signal. Because DynaSaur, AutoTools, and Tool-R1 use different datasets, models, metrics, and training setups, their numerical results should not be compared as though they were a shared leaderboard. [3][4][5]

## Learning when to call, and measuring the whole trajectory

A capable tool user must also know when not to call. When2Call distinguishes making a tool call from asking a follow-up question, acknowledging that tools cannot answer, or responding directly. Its reported 8B-model results show how training can alter this decision boundary: When2Call-RPO reached 52.4 macro-F1 and 70.0% length-normalized accuracy, compared with 31.9 and 49.1% for the named baseline, and the reported no-tool hallucination rate fell from 19% to 1.2%. Yet the paper also reports no uniform improvement on every call-task metric. The benchmark is synthetically generated and its scores are tied to its evaluation design. [7]

Final-answer scoring can hide mistakes in tool selection, arguments, or call order. TRAJECT-Bench proposes separate measures for exact trajectories, tool inclusion, argument/schema use, trajectory satisfaction, final answers, and retrieval. In the paper's parallel-query results, Claude-4 exact match fell from 0.846 on simple queries to 0.445 on hard queries, while tool-inclusion score on hard queries was higher at 0.668. That gap illustrates partial tool recovery without an exact trajectory. The authors also report that longer trajectories and dependent sequential calls are harder, and that retrieval can bottleneck hard queries. These findings diagnose distinct error sources, though the benchmark uses synthesized tasks and some measures rely on an LLM judge. [8]

Taken together, MetaTool, When2Call, and TRAJECT-Bench separate at least three questions: whether a call is needed, whether the selected tool fits the request, and whether the sequence of calls succeeds. [6][7][8] This separation is practically useful for debugging: a wrong final response might follow from a bad call/no-call decision, an irrelevant tool, invalid arguments, or a failure to use a returned observation. A single success rate cannot identify which step failed. Evaluation still has limits, including constructed tool pools, task-specific query distributions, and judge dependence. [7][8]

## Coordination and delegation

Multi-agent systems make tools and coordination roles part of the same problem. MultiAgentBench evaluates collaboration and competition through intermediate milestones and compares star, chain, tree, and graph arrangements. The authors report that graph coordination performed best among tested protocols in their research scenario and that cognitive planning improved milestone achievement by 3%. These findings suggest that topology and planning can influence benchmark outcomes, not that graph structures are always preferable. [9]

Tool-RoCo directly treats other agents as callable tools in multi-robot tasks. In the reported setting, cooperative tools accounted for 7.09% of selected tools, while activation tools accounted for 96.42%; the authors interpret this as rare requests for help and limited adaptive deactivation. The study makes delegation observable, but its robot tasks and tool definitions constrain generalization to text-only or workplace agents. [10] The earlier LLM-Coordination results also warn against treating coordination as one skill: understanding an environment and reasoning about partners or joint plans showed different performance patterns in that benchmark. [13]

For practice, these studies make the coordination structure itself a design variable. A central planner can assign work, while a graph or other decentralized arrangement changes how agents communicate and combine outputs. However, the available results vary in task, model, interaction protocol, and metric, so they do not establish a universal topology. Intermediate milestones and explicit records of delegation can make it easier to see where a team stalled or duplicated work. [13][9][10]

## Reliability, security, and oversight

Connecting an agent to real tools expands the consequences of mistakes. A retrieved page or document can contain instructions that conflict with the user's intent, and a tool call may exercise privileges granted to the agent. GrantBox evaluates privilege use with genuine tools under prompt-injection attacks. Its authors report that tested agents blocked some direct attacks but remained vulnerable to more sophisticated ones, with an average attack success rate of 84.80% in carefully crafted scenarios. This is a concerning result for that test set, not an estimate of real-world attack frequency. [11]

AgentSentinel proposes monitoring sensitive computer-use operations at the execution boundary. It correlates task context with system traces and can pause an operation for audit, then resume or terminate it. On its BadComputerUse benchmark, the authors report an 87% average attack-success rate across four tested LLMs and a 79.6% average defense success rate for AgentSentinel. The benchmark result shows a measurable defense in its evaluated setting, but the evidence retrieved does not establish production overhead or effectiveness across all tool environments. [14] GrantBox additionally describes isolation and request logging as part of its evaluation infrastructure, supporting a practical emphasis on limiting privileges, recording actions, and enabling recovery rather than relying only on the model to recognize malicious instructions. [11]

A separate oversight question is how users can inspect long-running agents. The HF Daily abstract for “What Did the Agent Actually Do?” introduces AgentMonBench to study whether monitors can identify consequential decisions and locate evidence that helps users assess them. Across eight models, the abstract reports improved decision identification and evidence localization in most settings compared with direct access to the original context. This supports reviewability in the tested settings, but does not establish that monitoring prevents attacks. [12] I read these security and oversight results as complementary: access controls limit possible actions, execution monitoring observes what is attempted, and evidence-grounded summaries can help a person review decisions. The retrieved studies test pieces of this approach, not a complete, validated deployment recipe. [14][11][12]

## Trends and open problems

The literature is moving from demonstrations of tool calling toward explicit measurement of action choice, arguments, trajectories, delegation, and consequences. Training work explores stronger tool representations and rewards, while benchmark work decomposes success into smaller decisions that can fail independently. [4][7][5][8] A practical implication is that evaluation should retain tool traces and distinguish a correct answer reached through an appropriate sequence from a lucky or unsafe outcome. TRAJECT-Bench is one example of trajectory-level scoring, and MultiAgentBench uses milestones to expose progress within collaborative tasks. [8][9]

Several problems remain open. First, results need more comparable evaluation: current methods use different models, tasks, tool pools, reward signals, and judges, so apparent gains may not transfer. [3][4][5][8] Second, agents need reliable recovery when a tool is unavailable, its output is ambiguous, or a multi-step plan goes wrong; DynaSaur reports recovery in selected tests, but the available notes do not establish broad robustness. [3] Third, tool permissions and untrusted content require testing under realistic interaction patterns. GrantBox's scenario-specific results and AgentSentinel's benchmark defense rate show that both attack and defense performance need careful contextual reporting. [14][11]

Finally, long-horizon systems need oversight that scales with the number and impact of actions. AgentMonBench makes consequential decisions and supporting evidence a benchmark target, while multi-agent work highlights sustained coordination and delegation as distinct concerns. The retrieved HF Daily evidence is abstract-level, and the collaboration studies are task-specific, so it remains unclear how well current monitors and team designs perform in sustained deployment. [10][12] For an implementer, the cautious takeaway is to evaluate tool choice and full trajectories, restrict permissions, log executions, and preserve evidence for review; the papers surveyed support these as design priorities, not as guarantees of safety or general competence. [7][8][14][11][12]
